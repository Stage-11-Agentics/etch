# ETCH-30: Crash recovery dead_pid path is dead code; crashes not recovered on next invocation

AUDIT ITEM 1 + SPEC AC#6. REPRO: drive session_start+user_prompt_submit+pre_tool_use then STOP (no session_end). Start a NEW session (session_start) in the same repo. EXPECTED per SPEC AC#6: 'the next Etch invocation commits [the .wip] as a partial record'. ACTUAL: the orphaned .wip remains; nothing is recovered until the 4-hour timeout elapses.
ROOT CAUSE: recovery/recovery.go ScanOrphaned recovers immediately only via the dead_pid branch (processAlive(pid)). But extractPID() reads a 'pid' field from the session_start event, and capture.SessionStartData (capture/session.go) NEVER records os.Getpid() -- the session_start hook writes no PID. So extractPID always returns 0 and the dead_pid branch is unreachable. Only the timeout branch (default 4h, config recovery_timeout_hours) ever fires. In a dense overnight run a crashed session can stay invisible for hours. NOTE: validation-report.md marked AC#6 PASS because TestDensityCrashRecovery INJECTS a PID into the .wip that the production binary never writes -- false confidence. FIX: write os.Getpid() at session_start and read it in recovery. Verified empirically in /tmp/etch-crash.
